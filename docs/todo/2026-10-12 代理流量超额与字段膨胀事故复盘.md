# 2026-10-12 代理流量超额与字段膨胀事故复盘

> 触发：老温报「服务器走的 qqpw 代理节点流量超额度了，回溯并归因」。
> 结论先说：**流量是「素材导出每轮重抓整个窗口」烧掉的，不是节点侧分流问题**；同一批改动还带出两个更严重的次生事故（每轮 OOM 停摆 + summary 字段指数膨胀）。
> 本文是本次事故的唯一事实源（数据、方法学、改动、验证、遗留）。

## 二、流量回溯（方法学 + 曲线）

**怎么量的**（没有现成的按天流量账，全靠重建）：
1. **单轮字节实测**：在服务器上用**流水线自己的抓取函数**（`article_content.fetch_article` + 计数字节的 Session）抽样 pending 条目 → gnews 条目 **710KB/条**（3 个请求：签名页 + batchexecute 解码 + 真实正文页），直连条目 **48KB/条**。
2. **每轮条数**：`journalctl -u green-policy.service` 里每轮的 `latest-24h.json: N 条待导出`（即 pending 数）。
3. **交叉验证**：eth0 累计 **163.6GB RX / 60.8GB TX**（开机 55 天 ≈ 3GB/天，含 8/17 前无代理时期）；nginx 出流量仅 20–66MB/天（站小）→ 隧道占 eth0 绝大部分，与逐轮估算（代理期合计 ~150GB）吻合。
4. **非导出流量实测**：采样一轮 eth0 → feed 抓取 5.2MB + 技术特征 4.9MB + 翻译 ~0.5MB ≈ **10.7MB/轮**。

**曲线**（`单轮导出字节 ≈ pending × 0.34MB`，单位 GB/天）：

| 日期 | 待导出/轮 | ≈GB/天 | 说明 |
|---|---|---|---|
| 8/24-27 | 63-82 | 0.6→1.5 | 代理 8/25 上线，导出刚接 |
| 8/28-9/30 | 150-200 | 2.6→3.3 | cac/Nature 等源扩充，窗口变大 |
| 10/1-10/3 | 188-204 | 3.2-3.5 | 平稳 |
| **10/4-10/6** | **124-150** | **2.2-2.6** | **索引 10/4 重建** → 命中率高 → 谷底 |
| 10/7 | 226 | 3.8 | 索引开始失效（窗口滑过重建点） |
| 10/8 | 297 | 4.9 | ↓ |
| 10/9 | 343 | 5.6 | ↓ + 1.1 补抓上线（当日 47 轮全量导出） |
| **10/10** | **397** | **~7**（含补抓 1.3） | 峰值；轮次开始被 OOM 打断 |
| 10/11 | 406 | 3.3 | 19 轮里多数没跑到导出 |
| 10/12 前 | — | ~0.1 | 已跑不到导出步骤（OOM） |

**关键机制**：`pending ≈ 窗口内「上次索引重建之后新增」的条目数` —— 重建后单调爬升直到占满整个 96h 窗口（~570 条）。所以**索引多久不重建，流量就爬多高**。

## 三、分流规则真相（节点侧零分流）

`/etc/mihomo/config.yaml`：`mode: global` + 只有一条 `GLOBAL` 组，**没有 `rules:` 段** → 凡连 `127.0.0.1:7890` 的请求全量走 `nat.qq.pw:35102`（出口 147.81.120.142，Hawaiian Telcom 家宽 AS36149）。分流完全靠应用层 `trust_env`：

| 走代理（夏威夷家宽） | 直连（`trust_env=False` / `proxies=None`） |
|---|---|
| 正文抓取 + 图片下载（export/refetch） | govcn/xinhua 正文（`_DIRECT_BODY_SITES`）、cac、澎湃、财新 |
| ~~RSS/feed 抓取~~（2026-10-12 改直连） | 东财/央行（`_NO_PROXY`）、Jev/TokenHub |
| ~~翻译 腾讯 TMT~~（改直连）、~~技术特征 SiliconFlow~~（改直连） | `NO_PROXY`：内网三网段 + 本机 IP |
| 空摘要补抓 | — |

⚠️ `docs/服务器部署与运维.md` 原写「仅正文抓取走代理」「每日几十 MB 级」**两处都不对**：RSS/翻译/技术特征此前也走代理（实际 GB/天量级）。

## 五、遗留与建议（未做完的部分）

1. **`Notes/.git` 911MB**：巨型 blob 在历史里，`git gc` 无法回收（可达对象）。要瘦身必须重写历史（filter-repo + force push）——**违反 AGENTS.md 的「禁止 force push」**，需老温单独决策；不改历史则仓库体积不会自己降。
2. **节点侧无流量账**：mihomo `log-level: warning` 只记失败连接，没有 per-connection 用量。建议给 mihomo 开 `external-controller`（只监听 127.0.0.1）后用 `/connections`、`/traffic` 采样，或用面板节点自带统计；否则下次仍只能靠日志重建。
3. **6 条历史摘要被早期修复版本截断到 2000 字**（`data/history.json` 里以 `…` 结尾、素材库无对应文件可还原）——内容损失有限，未再追。
4. **导出仍会重抓「没有正文的条目」**（过渡轮 pending 里 ~140 条）：这些是 WAF/收费墙站点，每轮重试属浪费。若要进一步省流量，可给导出加「失败冷却」（类似补抓的 7 天冷却）。
5. **补抓与导出仍在同一窗口抢同一条家宽出口**：已降频（每小时一批），若仍顶高可改到整点错峰或用 `--workers 1`。
6. **⚠️ 顺带发现的内容质量问题（非本次任务，但有实证）**：恢复 git 提交后，素材库一次性入库了 10/10-10/11 积压期间抓到的一批**垃圾/色情标题条目**（如 `政策/欧盟/欧盟委员会/2026-10-10 SEX~VIDEO~XXX.md`、`2026-10-11 Indo Sex Viral Porn Videos.md`），来源是欧盟委员会 / 美国 EPA 这类**被投毒的 RSS 条目**。现有过滤（`_is_nav_junk_title` / NOISE 词）没覆盖这类英文色情/赌博关键词 → 建议补一条英文垃圾词硬过滤（SEX/VIDEO/PORN/CASINO 等，标题级命中即丢）并把已入库的清理掉。
