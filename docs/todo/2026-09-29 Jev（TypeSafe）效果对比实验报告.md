## 二、实验设计

- **样本**：`data/history.json` 近 30 天池（1222 条）随机分层抽 384 条，seed=20260928，快照 `data/sample-snapshots/jev-bench-n384-seed20260928-20260928T144948Z.json`（另有一轮近 7 天 228 条作补充口径）
- **Jev 轨**（五问一次请求，与 P0 同口径：is_green/is_noise/sub_dim/strength/topic）：
  - `serial`＝主流程真实路径（`jev_client.evaluate`，QPS10 限流+熔断）
  - `c8`/`c16`＝probe 自带线程池直连网关（同 payload；主链路未动）
  - 外围重试 ×2（上游 503 时 1.5s 退避），重试数单独计量
- **LLM 轨**：DeepSeek V4 Pro / Flash（SiliconFlow，`score_diff_monitor.build_prompt` 同款强度单问；与 Jev 五问的口径差在对比时注明），8 并发
- **成本口径**：Jev 双计——厂商 token 价 $0.042/M input（output 免费）× 决策单价 $24.57/M 次（均为 09-23 讨论稿校准值）；token 用量取自响应 `usage` 实测（384 条全量计量）
- **模型版本**：`TypeSafe/jev-latest`（TokenHub 网关）。09-28 核对上游仍只有 `jev-latest`/`jev-preview`，**自 09-23 起无新版本**，两轮实验同版本，可比

## 三、E2：384 条吞吐/成本基准

### 3.1 速度（384 条，2026-09-28）

| 轨道 | 总耗时 | 吞吐（条/s） | 单条 p50 | p95 | 失败 |
|------|--------|------------|---------|-----|------|
| Jev 并发 16 | **12.0s** | 32.0 | 0.277s | 0.352s | 0/384 |
| Jev 并发 8 | **23.6s** | 16.3 | 0.272s | 0.373s | 0/384 |
| **宣传口径** | **24.9s** | 15.4 | — | — | — |
| DeepSeek Flash（8 并发） | 146.7s | 2.62 | 1.91s | 8.26s | 0/384 |
| DeepSeek Pro（8 并发） | **1487.6s（24.8 分钟）** | 0.26 | 25.11s | 67.03s | 4/384 |
| Jev 串行（主流程形态） | ~148s—775s* | 0.5~2.6 | 0.281s* | 4.887s* | 0/384 |

\* 串行说明：正式 384 轮的串行阶段进程跨夜被系统挂起，**wall 值无效**（68717s 为挂起时间污染）；表内取其**有效逐条延迟**（p50 0.281s，QPS10 限流下理论上限 ~2.6 条/s → 384 条约 148s），并用 228 条补充轮的实测串行（455.3s、0.5 条/s、p50 1.99s，上游劣化时段）作保守上界（384 条约 775s≈13 分钟）。**真实区间 2.5~13 分钟，取决于上游时段**。

### 3.2 成本（384 条，实测 token 计量）

| 轨道 | input tok | output tok | 成本 | 说明 |
|------|-----------|-----------|------|------|
| Jev（五问/条） | 433,515 | 58,368 | **$0.0182**（token 口径）/ $0.0094（决策牌价口径） | 1,281 tok/条；TokenHub 渠道未配价，平台实收 $0 |
| **宣传口径** | — | — | **$0.19** | 折合 $0.000495/条，为实测 token 口径的 ~27 倍 |
| DeepSeek Pro | 247,028 | 313,770 | **≈$0.37~1.48（¥2.6~10.5）**（实测 token，按第三方报价区间 ¥3~12/M in、¥6~24/M out 折算，官网为准） | output 817 tok/条为隐藏推理 token，占成本大头 |
| DeepSeek Flash | 219,329 | 13,621 | ≈¥0.25（≈$0.035，按 ¥1/M in、¥2/M out） | 唯一与 Jev 同成本量级的轨道，但打分已知系统性偏低 |

- Jev「五问一次请求」的 token 效率是关键：**每条新闻 5 个判定只花 1281 token**（DeepSeek Pro 光强度一问就要 in 649 + out 821/条，output 大头是隐藏推理 token——228 轮实测 output 187k > input 148k）。
- 与宣传成本的关系：$0.19 ≈ $0.0005/条，恰是本项目 09-23 讨论稿**已修正掉 13 倍的早期高估口径**；按厂商 token 实测价 384 条只要 $0.018。宣传口径高估了，但方向对 Jev 有利（实际更便宜）。

### 3.3 上游稳定性（新发现，09-28）

1. **503 风暴**：实验首时段（UTC ~13:30）上游连发 `provider_upstream_unavailable`（HTTP 503），无重试时串行失败率 ~40%（12 条冒烟 5 败）；并发更糟
2. **延迟劣化 5 倍**：同期 p50 0.36s（09-23 校准）→ 1.8~2.0s
3. **数小时后自愈**：c8/c16 阶段 p50 回到 0.27s、零失败；09-29 复测健康
4. **对策已落地**：本轮 probe 内置重试 ×2（1.5s 退避）后 0 失败跑完 384×3 轨；09-29 已把重试正式补进 `jev_client.evaluate()`（快速失败类 ≤2 次 0.8s 退避、慢超时不重试、熔断按逻辑调用计，负向测试+自检通过）。

### 3.5 关联发现：SiliconFlow V4-Pro 端点持续故障（可用性风险）

09-28 上午起 SF 的 `DeepSeek-V4-Pro` 持续返回 `HTTP 503 code=50508 "System is too busy"`（单发秒败，持续 >12h），Flash 不受影响。384 条 Pro 轨两轮全灭；09-29 晚恢复后第三轮跑通（1487.6s、4 失败、p50 25.1s——比故障前的 228 轮实测还慢 40%，恢复后性能也未完全回到故障前水平）。**这直接威胁项目现有打分双轨（score_diff_monitor 依赖 Pro）——Pro 不可用时双轨观察自动退化为单轨，建议 sdm 加 flash 回退**（Flash 打分系统性偏低是已知偏差，作参照轨仍优于空）。

### 3.6 关于「碾压 Opus 5」

未测 Opus（本机无该轨道，经老温确认用 DeepSeek 双轨替代）。但 Pro 已是「慢而贵」的 LLM 代表（p50 17.5s/条）：若宣传以 Opus 为基准确实成立；只是**碾压的是 LLM 这一类，不是「快模型」全部**——Flash 吞吐 3.1 条/s、成本同量级，输 Jev 5 倍速度但赢在能生成解释文本。Jev 的本质优势：**决策判定不生成文本，token 开销低一个量级**。

## 五、结论与建议

1. **速度/成本宣传口径：核实成立**（23.6s/384 条 @ 8 并发 ≈ 宣传 24.9s；成本实际更便宜一个量级），但有三个前提要写进任何采纳决策：
   - 需要**并发改造**（现 jev_client 串行 QPS10 形态只有 0.5~2.6 条/s）
   - 需要**重试**（上游 503 时变；本轮重试后 0 失败）
   - 决策模型只会「答题」不会「解释」，token 省的原因也是它不能替代 LLM 写摘要的原因
2. **Pro 触发塌陷红线（85.7% 落兜底档）是本次最大意外**：项目打分双轨的 LLM 侧按自家验收标准已不可作强度判定器。关联工程项已完成：`score_diff_monitor` Pro→Flash 自动回落（09-29 ✅）；`jev_client` 重试已补（09-29 ✅）。剩余优先级最高的是**老温标注 gold set**（唯一能定谁对的人工信尺）
3. **质量判定继续等 gold set 人工标注**（预登记已冻结，随时可终审）：标注完成后跑
   `python scripts/gold_set.py evaluate --judges kw,jev,pro --form C`
4. **七细类信号持续偏正面**（分歧初审 Jev 对 ~82% + kw 四类系统性错误模式明确），维持「gold set 终审后从七细类切入」的既定顺序；kw 的关键词组可先行修四类误伤（金融词抢跑 / 国际词过触发 / 政策库默认兜底 / "研究"宽词）
5. **P2 影子模式的技术顾虑已解除**：384 条 12~24s、$0.018/轮，每天一轮 96h 窗口全量（~1200 条）成本 < $0.06/天，影子写入主流程数据完全可行

- **kw 兜底分问题（P0.5 问题①）的答案：大体不冤**——gold 本来就有 52% 常规级，kw 底部堆积 60.2% 与真实分布接近；真问题是顶档虚高 + 细类错分，不是底部堆积

## 七、v5.2 收紧后复评与基线修正（2026-09-30，**修正 §6.2 结论**）

> §六 是 2026-09-29 的终审记录，**保持原样不改**；本节记录次日发现的一处方法学问题与复评结果。**读 P3 决策依据时以本节为准。**

### 7.1 发现：kw 轨基线被低估（方法学错误）

`gold_set.py evaluate` 的 kw 轨原用**抽样时冻结的 `sub_kw`** 判定，而 `gold-set.jsonl` **不含 `site_id` / `library` 两个字段**——`categorize_dimension()` 恰恰依赖它们（`library=policy` 才是「政策库默认」、外源政府站点要靠 `library=policy` + 站点白名单改判国际动态）。后果：kw 细类命中率被系统性压低。

**修正**：`gold_set.py` 新增 `history_meta()` + `live_sub()`，按 `url` 从 `data/history.json` 反查真实 `site_id`/`library` 后**实况重算**细类与强度。

| 七细类命中 | 原记录（§6.2） | 修正后（v5.2 前冻结基线重算） | v5.2 收紧后 |
|---|---|---|---|
| kw | 45.8% | **52.4%**（同日同码复算） | **52.4%** |
| jev(choice) | 59.0% | 57.1%（同轮重跑，84 条） | — |

→ **Jev 对 kw 的七细类优势：+13.2pp → +4.7pp**。§6.3 的「证据齐备、建议立即切换」应降级为「**收益有限，需重新权衡性价比**」。

### 7.2 v5.2 收紧后的强度复评（84 条，同日同轮）

- 收紧前 kw 42.2% / jevC 45.8% → **收紧后两轨在「完全命中」上已打平**（48.8% vs 47.6%）
