## WSL 操作服务器（2026-08-14 沉淀，2026-08-19 修正）

**核心事实**：
1. **WSL ssh/scp 直连可用（2026-08-19 实测）**：`moltbot260130.pem` 在 `/mnt/c` 挂载下权限是 0444/0777，OpenSSH 报 `Permissions too open` 拒绝——**复制到 WSL 原生路径 + chmod 600 即可直连**：`cp /mnt/c/Users/wenyu/.ssh/moltbot260130.pem /root/.ssh/ && chmod 600 /root/.ssh/moltbot260130.pem`。本会话全程用 WSL ssh/scp 完成部署（避开 cmd.exe 引号坑）
2. `sg-moltbot` 别名只在 Windows 的 `~/.ssh/config`，WSL 里没有 → WSL 下用 `ssh -i /root/.ssh/moltbot260130.pem root@47.82.211.111`
3. `/opt/green-hot-news` **不是 git 仓库**——代码同步靠 **scp 推送**，不拉 GitHub
4. 本机 DNS fake-ip 劫持：一律用 IP `47.82.211.111`，不用域名 ywm.life

**模板 0：WSL 直连（agent 首选，2026-08-19 实测）**

```bash

# 远程命令（无引号嵌套问题）
```

**模板 3：复杂命令 / scp 传文件 → 写 .bat 到项目根目录再执行**

```bat

set SSH=C:/Windows/System32/OpenSSH/ssh.exe
set SCP=C:/Windows/System32/OpenSSH/scp.exe
set REMOTE=root@47.82.211.111
"%SSH%" -i %KEY% -o IdentitiesOnly=yes %REMOTE% "cd /opt/green-hot-news && .venv/bin/python -c \"import ast; ast.parse(open('scripts/update_news.py').read()); print('syntax OK')\""
"%SCP%" -i %KEY% -o IdentitiesOnly=yes C:\Users\wenyu\Documents\Obsidian_wen\green-hot-news\scripts\update_news.py %REMOTE%:/opt/green-hot-news/scripts/update_news.py
"%SSH%" -i %KEY% -o IdentitiesOnly=yes %REMOTE% "md5sum /opt/green-hot-news/scripts/update_news.py"
```

**代码同步流程**：本地改脚本 → scp 上传 → 服务器语法检查 → 测试运行（`--output-dir /tmp/gpn-test` 不碰生产）→ systemd timer 每 30 分钟自动用新脚本跑（无需重启）。

**⚠️ 部署时机坑（2026-08-26 实测）**：systemd timer 每 30 分钟跑一轮（fetch 约 1-2 分钟、翻译数分钟、总时长 ~13 分钟）。若 scp 落在**抓取进程运行期间**，本轮抓取用的仍是**启动时已加载的旧代码**（Python 模块启动即载入），新代码要等下一轮（+30 分钟）才生效。后果：新抓的条目按旧逻辑产出（如摘要 HTML 残留），QA 分骤降。**规避**：① scp 前 `systemctl is-active green-policy.service`，若 `activating` 说明正在跑，等它 `inactive` 再传；② 若已踩坑，重新跑 `backfill_clean_summary.py`（清存量）+ `migrate_dimensions.py`（重打分）即可补齐，无需等下一轮。

**⚠️ qmd 导出超时坑（2026-09-03 实测）**：源增至 77 个后 qmd 导出（正文抓取+图片下载，24h 窗口 ~190 条）单轮需 ~15-18 分钟，超过 unit 原 `TimeoutStartSec=900`（15 分钟）→ systemd 杀进程，连续两轮死在"进度 140/188"，**步骤 2/3（Notes git push、站点数据 commit）与 qa_report 全部停摆**（data 主文件在导出前已写完，网站不受影响）。已改 `/etc/systemd/system/green-policy.service` `TimeoutStartSec=2400`（40 分钟）并 daemon-reload。判断超时：`systemctl status green-policy.service` 显示 `result 'timeout'` + journalctl 尾部在"进度 N/xxx 待导出"处戛然而止。注意 scp 前 is-active 若为 `activating` 可能是超时杀进程前的漫长导出期，等它变 `inactive`（被杀后）再传。⚠️ 本机（2026-09-03）实测 WSL 侧 `git push` 报 `could not read Username`（GCM 仅 Windows 侧可用），GitHub 推送需走 cmd.exe 模板。

### 多终端并行开发纪律（2026-08-19，与 AGENTS.md 一致）

老温会同时开多个终端写不同功能。**不用分支隔离**（同一工作目录下 `git checkout` 会重写工作区文件互相踩踏；独立 clone 又太重）。三层纪律：

1. **提交纪律**：commit 前 `git diff HEAD --stat` 确认改动范围；只 add 自己负责的文件；update_news.py 单文件多人改用 `git add -p` 挑自己的 hunk，**不把别人的半成品带进自己的 commit**
2. **区域约定**：update_news.py 按功能区域切（fetch 函数区 / BUILTIN_SOURCES / SOURCE_SCORE / SITE_LAYOUT / 关键词区 / 白名单组），并行会话各写各的区域冲突最小
3. **部署纪律**：谁收尾谁 scp；scp 前 md5 对比确认同步方向；部署前 `py_compile` + 确认 BUILTIN_SOURCES 注册无悬空引用（防半成品崩服务器 timer）。实例：2026-08-19 另一终端 290 行"国际智库/投行"半成品被整文件 scp+commit 带上——好在代码完整未崩，但应避免

**踩坑速查**：WSL ssh 直连 ✓（密钥复制到 /root/.ssh + chmod 600，见模板 0；旧说法"WSL 连不上"已过时，2026-08-19 实测）| `/c/...` 路径 ✗（git sh 不认）| cmd 单行塞复杂命令 ✗（引号嵌套炸）| cmd 单行单引号 ✗（cmd 不认单引号）| cmd 单行转义双引号 ✗（三层转义失真）| **.bat 含中文 ✗（UTF-8 被按 GBK 解析，乱码连累全文件）** | 服务器 `git pull` ✗（非 git 仓库）| `ssh sg-moltbot`（WSL）✗（别名在 Windows）| 域名 ✗（fake-ip 劫持）。判断标准：WSL 直连优先，cmd.exe/.bat 仅 Windows 侧（Obsidian Git 插件）场景用。

### 可移植性两条坑（2026-10-04 新增，动文件名逻辑前必读）

vault 与服务器共享同一 git 树，文件名必须**同时**满足 NTFS 与 ext4：

| 坑 | 症状 | 根因 | 修法 |
|---|---|---|---|
| 文件名 > 255 **字节** | 服务器 `git reset --hard` 报 `unable to create file …: File name too long`，整棵树落不下来（本地 NTFS 上限是 255 UTF-16 字符，日文标题 80 字 = 240 字节 + 日期 + ` 【dupN】` = 263 字节） | `export_qmd._safe_filename` 按**字符**截断 | `_NAME_TITLE_BYTES = 200` + `_clip_bytes()` 按 UTF-8 字节裁剪；存量 1 个文件改名（`cache/_fix_long_name.py`） |
| 同目录**大小写**重名 | 本地 `git status` 永远显示 1 条 modified（`Hurricane POLO.md` / `Hurricane Polo.md`），实际只有一份内容 | ext4 区分大小写，`target_path` 防覆盖检测用 `path.exists()`（大小写敏感） | `target_path` 改走 `_ci_existing()` 大小写不敏感查重；存量 1 组改名 `…〔mat-52f93d〕.md`（`cache/_fix_case_collision.py`） |

两端都可跑的体检（5 项全 0 才算干净）：

```bash
python3.11 scripts/audit_vault_portable.py [Notes/素材库]
# 1 文件名 >255 字节 / 2 大小写不敏感重名 / 3 Windows 非法字符 / 4 Unicode 归一化重名 / 5 全路径 >250 字符
```

### agent 侧操作要点（2026-10-04 踩坑沉淀）

1. **本地 push 被沙箱挡**：DSH 沙箱下 git 走 MSYS `sh.exe` 建命名管道失败（`couldn't create signal pipe, Win32 error 5`）→ 设 `GIT_SSH=C:\Windows\System32\OpenSSH\ssh.exe`（**GIT_SSH 只接受裸程序路径**，`GIT_SSH_COMMAND` 带空格参数会被 sh 解析而再次踩坑）后 push 正常。
2. **别把 git 的输出接 `Select-Object -First N`**：PowerShell 提前关管道会打断 git 的 checkout（实测 ff merge 在 59% 被腰斩，工作树少 101 个文件且 `git status` 只报 1 条）→ 重定向到文件再读。
3. **.bat 必须是 ASCII + CRLF**（`cache/_crlf.py`），且**不要出现 `%s` 之类 `%` 字面量**（cmd.exe 会当参数展开，实测把 `printf '%s %s'` 展成 `s`）。
4. 中文路径一律放进 scp 上去的 Python 驱动脚本（`cache/_cutover_server.py`，分 step 0-5 可逐步核对），命令行保持 ASCII。

### Jev（TypeSafe）判定通道（2026-09-30 上线）

**背景**：Jev 的判定链路原先整条长在老温 PC 上（家宽 TokenHub 网关 + 上游 key），服务器上既无通道也无凭证 → 服务器侧判定"跑不起来"。**现改为服务器直连 TypeSafe，不依赖 PC。**

| 变量 | 值 | 说明 |
|---|---|---|
| `JEV_DIALECT` | `native` | `native`=直连 TypeSafe；`tokenhub`=经网关（本机默认） |
| `JEV_BASE_URL` | `https://api.typesafe.ai` | native 模式基址（`jev_client` 会自动去掉尾部 `/v1` 防重复） |
| `JEV_MODEL` | `jev-latest` | 实际解析为 `jev-1.13.0` |
| `JEV_PATH` | `/v1/systemone` | 判定接口路径 |
| `JEV_API_KEY` | `<TypeSafe 上游凭证>` | 服务器侧直连凭证（**只写不打印**） |
| `JEV_SHADOW` | `1` | **P2 影子模式总开关**；改 `0`/删行 = 完全停用（回退开关） |
| `JEV_SHADOW_MAX` | `600` | 每轮判定条数上限（成本护栏） |

- `jev_client._load_cfg` 读取顺序：环境变量 → `ROOT/.env` → `/etc/green-policy.env`，**无需改 systemd 单元**
- 实测：服务器直连 `POST /v1/systemone` **200 / p50 0.29s**；全量一轮 ≈470 条 ≈40s
- 影子结果：`rec["jev_shadow"]`（`score` 不动）+ 聚合报告 `data/jev-shadow-report.json`
- 验证命令：`ssh sg-moltbot "grep -c '^JEV_' /etc/green-policy.env"`（应为 6）；查影子是否真跑：`journalctl -u green-policy.service | grep 'Jev 影子'`

#### ⚠️ 远端 shell 脚本必须 LF（2026-09-30 踩坑）

在 Windows 上写 `.sh` 再 scp 到服务器，若文件是 **CRLF**，`KEY=$(cat /tmp/x)` 会取到带 `\r` 的值 → 请求头变成空 → TypeSafe 返回 **403 `Must supply an API key!`**（看起来像密钥错误，其实是换行符）。**scp 前必须转 LF**：

```powershell
$s = "$env:TEMP\x.sh"; $c = (Get-Content $s -Raw) -replace "`r`n", "`n"; [System.IO.File]::WriteAllText($s, $c)
```

同类坑：PowerShell 会在**本地**先展开双引号 ssh 命令里的 `$(...)` —— 远端命令一律写成 `.sh` 文件再 `ssh host "sh /tmp/x.sh"`。

## 双向同步竞态修复（2026-08-14，素材层 git）

**现象**：服务器 systemd 日志偶发 `green-policy.service: Failed with result 'exit-code'`，抓取成功但 git push 报 non-fast-forward 被拒 → set -e 下整个服务 FAILURE。根因：服务器每 30 分钟 push 素材库 + 本地 Obsidian 插件每 30 分钟 autoPush，两边都基于旧 base 提交；且旧 sync.sh **只在有新提交时 push、从不 pull**，服务器工作区与远程越走越远。

**修复（sync.sh 素材层段 v2）**：
1. 无论有无本地提交，先 `git pull --rebase -X theirs origin master` —— 整合本地 Obsidian 已推送的提交
2. `-X theirs` 关键：索引文件（ai-index.md / 媒体库.md / 政策库.md）两端都会重写，冲突**必然发生**，自动取远程（本地 Obsidian）版本，rebase 不中断；服务器新笔记正常重放
3. push 失败只提示（下周期自动重试），**不在失败分支里嵌套 pull**（会二次触发 rebase 卡死）
4. 服务器 Notes 仓库配置了**仓库级** user.name/user.email（green-policy-bot）——rebase 重放提交需要 committer identity，旧脚本只用了命令级 `-c` 配置，rebase 不认，直接 fatal

**踩坑记录**：
- rebase 需要 committer identity：`git -C Notes config user.name green-policy-bot && git -C Notes config user.email bot@ywm.life`
- 历史积压（39 个未推送提交）用 `git pull --rebase -X theirs` 一次性重放成功
- 误操作提交清理用 `git rebase --skip`（内容全弃）而非 reset --hard（老温禁止）
- **WSL git 看 Notes 状态全是 M（行尾符幻觉）**：WSL git autocrlf=false 对比 CRLF 工作区 vs LF blob 永远显示修改；**必须以 Windows git（cmd.exe 模板）为准**（Obsidian 插件同环境）
- rebase 切换分支时未跟踪文件与目标树同名会阻塞（"could not detach HEAD"）：先把冲突的未跟踪文件 mv 到 /tmp 备份，rebase 完成后再判断恢复
