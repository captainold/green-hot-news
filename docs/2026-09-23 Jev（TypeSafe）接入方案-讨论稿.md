## 一、Jev 是什么（先对齐概念，别按 LLM 的思路理解它）

| 维度 | 事实 | 出处 |
|------|------|------|
| 定位 | **System One 决策模型**，不是 LLM：不生成文本、不返回思维链/解释，只回答**受约束的类型化问题** | [TypeSafe docs · Primitives](https://docs.typesafe.ai/primitives) |
| 三个原语 | `noul`（是非，返回 yes 概率 0~1）／`choice`（多选一，返回 choice + probabilities + confidence，最多 255 项）／`score`（有序量表，2~10 档，返回概率加权位置 + legend + confidence） | 同上 |
| 接口 | **不是 chat/completions**：`POST https://api.typesafe.ai/v1/systemone`（body：`model` / `state` / `questions`）；亦可走 OpenRouter `POST /api/alpha/decisions`（`typesafe/jev-1.13`）或 Vercel AI Gateway | [OpenRouter Jev 教程](https://openrouter.ai/docs/guides/community/jev-tutorial)、[apidog 指南](https://apidog.com/blog/jev-api-key/) |
| 官方设计要点 | ① 一次请求可问多个问题，**并行、互不可见**，加问题几乎不加时间、只加少量 input token；② 答案被**约束在你给的选项内**，不需要解析自由文本；③ 建议把复合判断**拆成多个问题**，权重留在自己代码里；④ 用 `confidence` 做**置信度路由**（高置信自动、低置信升级人工） | [Primitives](https://docs.typesafe.ai/primitives) |
| 第三方实测（2026-09-19，300 次真实调用，单次问 3 个判断） | p50 **0.527s** / p95 0.813s；$24.57 / 百万次决策（单次 ≈ $0.0000246，均 585 input tokens）；output token 免费；与模板标签一致 91.3%（**注意：模拟数据 + 模板标签，不是真实准确率**） | [robokrunch/jev-physical-ai](https://github.com/robokrunch/jev-physical-ai) |
| 厂商口径 | 70–500ms 延迟、$0.042 / M input tokens、output 免费 | 同上（标注为口径，非我实测） |
| 中文 | 第三方基准用的是**中英双语**模板（CN/EN），可用；但**中文真实新闻上的准确率无人测过** | 同上 |
| 我本机验证 | `POST https://api.typesafe.ai/v1/systemone` → **403 authentication_error**（路由存在、仅缺 key），本地**无需代理**可达 | 2026-09-23 本机探测 |

**一句话**：Jev 是"**判定器**"，不是"生成器"。它的能力边界正好落在我们目前用关键词和慢速 LLM 硬扛的那一块。

## 三、能力边界：Jev 该接哪、不该接哪

**适合（判定类，输出受约束，正是关键词的弱区）**

| 候选接入点 | Jev 原语 | 现值 | 价值 | 风险 |
|---|---|---|---|---|
| ① 相关性门控 `is_policy_relevant`（AI_MEDIA / X / allnet / radarai / TECH_SITES 的模糊带） | `noul` | 关键词白/黑名单 + 词边界正则 | 中高：减少"八卦误入"与"真绿色新闻漏收" | **低**（只影响入库边界） |
| ② 七细类分类 `categorize_dimension` | `choice`（7 项） | 100+ 关键词 + 12 级优先级瀑布 + 大量特例 | **高**：分类是三层导航与强度判据的前置，错了会连锁 | 中（会改变现有分布） |
| ③ 内容强度 `score_content_strength` | `score`（4 档） | 关键词档位，**62.3% 落兜底** | **高**：直接补上最弱的一维 | **高**（动铁律 3） |
| ④ 主题相关 `score_topic` | `score`（4 档） | 关键词三档，37.5% 落 6 分 | 中高 | 中 |
| ⑤ 噪音/仪式稿/榜单/导航 | `noul` | 黑名单 + 人工发现（如"揭牌仪式"虚高、"美国DOE 注册邮件更新"被收录） | 中 | 低（只降权不删除） |
| ⑥ 同事件去重（`merge_history` ±72h 相似合并） | `noul`（state 放两条标题） | 标题相似度/前缀桶启发式 | 中，但成本 = O(候选对) | 低 |
| ⑦ 素材库 md 互链精选（现 SiliconFlow V3，1.9s/条） | `choice` | LLM 生成式精选 | 中 | 低 |

**不适合（生成类，Jev 做不到）**：`tech_feature` 提取（一句技术特征）、标题翻译（腾讯 TMT）、日报/摘要生成、正文抽取。——这些继续用现有方案，**不要试图让 Jev 代劳**。

**P0 实测后修正的一条边界（2026-09-23）**：上表 ③④ 里的"档位打分"比预想的难——
**Jev 在闭集选择（choice：七细类）上表现最好，在"给绝对档位"（score：内容强度/主题相关）上
在本语料里没有区分度**（与 Pro 0/30 一致、97% 落最高两档、加频率锚点也无效）。
教训（可推广）：**决策模型擅长"从给定选项里选 / 回答可证的是非"，不擅长"无锚点的绝对刻度"**。
所以接入方式要改成"**问可证的是非，档位在代码里合成**"（权重与逻辑留在调用方，正是官方设计要点），
而不是让 Jev 直接输出 30/25/20/8 这种绝对分。

## 四、推荐结合方式：一次请求、多维判定、公式不变、置信度路由

### 4.1 总原则（这条要老温点头）

> **打分公式不变，只换判定器。**

- 六维权重、等级线、七细类定义 **仍以 `docs/标准文档/打分体系标准.md` 为唯一权威**；权重写在我们的代码里（Jev 官方也建议"权重留在自己代码里"，见 Primitives 文档）。
- Jev 只替换「关键词判定器」这一层实现；输出经我们代码合成后，字段结构与含义完全不变（`score` / `score_breakdown` / `dimension` / `sub_dimension`）。
- 因此 **不新增第七维、不引入第二套评分体系**，前端与 `score-standard.html` 无需改语义。

### 4.2 请求形态（一条 item = 一次请求，5 问并列）

```json
POST /v1/systemone
{
  "model": "jev-1.13",
  "state": {
    "title": "江苏光伏装机规模突破 1 亿千瓦",
    "summary": "……",
    "source": "中国能源报",
    "library": "media"
  },
  "questions": {
    "is_green":  {"type": "noul",  "instructions": "这条内容是否与绿色低碳/气候/能源转型直接相关？",
                  "criteria": {"true": "直接涉及…", "false": "仅泛泛提及或无关"}},
    "is_noise":  {"type": "noul",  "instructions": "是否为无实质信息的仪式/揭牌/榜单/广告/导航类内容？"},
    "sub_dim":   {"type": "choice", "instructions": "这条内容属于哪一细类？",
                  "criteria": {"政策法规": "…", "国际动态": "…", "技术研发": "…",
                               "基础研究": "…", "社会创新": "…", "企业经营": "…", "金融资本": "…"}},
    "strength":  {"type": "score", "instructions": "这条内容的强度处于哪一档？",
                  "criteria": ["里程碑级（国家级/全球级开创性事件）", "重要级（高规格推进/关键节点）",
                               "进展级（有实质内容的常规进展）", "常规级（无强信号的普通条目）"]},
    "topic":     {"type": "score", "instructions": "主题与本雷达核心议题的相关程度？",
                  "criteria": ["核心议题（碳市场/碳价/双碳…）", "重要议题（新能源/储能/氢能/AI…）",
                               "一般议题（节能/环保/气候/绿色…）", "弱相关"]}
  }
}
```

**两个关键设计约束（来自 Jev 的机制，照抄官方例子会踩坑）**：

1. **同一请求内的问题互不可见** → 不能问"按 `sub_dim` 的结果给默认分"。所以 `strength` 的档位描述必须与细类无关（4 档：里程碑/重要/进展/常规），**"常规级 → 10 还是 8" 由我们的代码按 `DEFAULT_STRENGTH_BY_SUB[sub]` 映射**。这恰好把"公式的权威"留在了我们这边。
2. **`score` 的 `score` 是概率加权位置（可落在两档之间，如 1.99）** → 合成时用最近档 + 保留 confidence，低 confidence 触发回落。

### 4.3 合成与回落（置信度路由）

```
Jev 答案（含 confidence）
   ├─ confidence ≥ 阈值 且 is_green 明确 → 采用 Jev 判定，按 v5.1 公式合成 score
   ├─ confidence < 阈值 或 请求失败      → **回落现有关键词判定**（静默降级，主流程不受影响）
   └─ is_noise 高置信                  → 只降权/打标，不删条目（避免误杀不可逆）
```

### 4.4 新增模块与开关（照 `tech_feature.py` 的成熟范式）

- `scripts/jev_client.py`：key 读取顺序（环境变量 → `.env` → `/etc/green-policy.env`）、QPS 控制、**熔断**（401/402/403/429 立即熔断）、超时、静默降级、结构化返回。
- `data/jev-cache.json`：按**规范化标题 key** 缓存（同 `tech-feature-index.json` 的做法——Google News 聚合 URL 每次抓取都变，按 URL 缓存永不命中，这个坑 8-23 已经踩过一次）。
- 开关：`--jev` / `GREEN_USE_JEV=1`，**默认关**；服务器 timer 在 P3 通过验收前不打开。
- 版本钉死：`model: jev-1.13`（不要用 `jev-latest`——阈值要在固定版本上校准）。

### 4.5 规模与成本（基于本仓库实测 580 条/轮）

| 场景 | 调用量 | 成本 | 耗时 |
|---|---|---|---|
| 全量、无缓存（最坏上界，585 tokens/次） | 580 × 48 = **27,840 次/日** | ≈ **$0.69/日 · $20.5/月** | 串行 5.1 min/轮；并发 4 → **1.3 min/轮** |
| 全量、若我们的 criteria 更长（1.5k tokens/次） | 同上 | ≈ $1.7/日 · $52/月 | 同上（问题并行，加问题不加时间） |
| **接缓存后**（每日真正新条目 ~365–500 条） | 365–500 次/日 | ≈ **$0.01–0.03/日** | 可忽略 |

> **✅ 已用平台数据校准（2026-09-23，复盘问题④）**：TokenHub `/api/admin/api-keys/{id}/usage` 显示本项目 key
> `green-hot-news` 累计 **323 次请求 / 1 次失败 / 输入 291,165 tokens / 输出 26,992 tokens**
> → **985 tokens/次**（比原假设 585 高 1.7 倍）。按最坏上界（580 条 × 48 轮 × 30 天 = 83.5 万次/月）重算：
> **≈ $3.2/月（$0.000038 × 83.5 万）**，即原表 $20.5/月 属于"按决策单价 $24.57/M"的口径，两种口径差 ~6 倍，
> **都远低于任何需要犹豫的量级**；带缓存后按实测口径 ≈ **$0.014–0.019/日**。
> 另外平台记录的那 1 次失败是 **`provider_upstream_error`、耗时 40,175 ms** —— 正是问法实验里那条失败样本，
> 说明**失败来自上游超时（~40s）而非我们的客户端**；失败率 1/323 ≈ **0.3%**。

> 30 分钟 timer 容得下（哪怕全量最坏情况也只占 1.3 分钟，相对抓取本身的数分钟是零头）。
> 若按厂商活动口径的 1.2 亿 token 额度算：约 **12 万次调用** ≈ 全量跑 4 天，或**带缓存跑约 10 个月**。

## 六、必须先正视的三个风险

### 最大收获：绝对档位 vs 可证的是非（这条比"Jev 行不行"更重要）

同一批 30 条、同一个模型、只换问法，三种形态：

|---|---|---|
| A 现状四档（定性描述） | 12 / 15 / 2 / 1 | 13.3% |
| B 频率锚定四档（"里程碑约占 2~5%"） | 11 / 14 / 5 / 0 | 26.7% |
| **C 三个可证的是非 + 代码合成档位** | **0 / 5 / 13 / 12** | **33.3%** |

**C 的措辞一改，分布立刻从"顶部塌陷"翻成"底部塌陷"**（2026-09-23 复跑，把 `is_routine` 从"普通条目"
改成可数判据"是否缺少可验证的实质信息"）：分布变成 **0 / 4 / 5 / 20**、与关键词一致率升到 **44.8%**（29 条有效，1 条调用失败）。
→ 结论更硬了：**问法能自由地把分布推向两端的任意一端，所以"一致率高低"本身不能作为选型依据，
必须在人工 gold set 上比准确率与混淆矩阵**（这正是 P0.5 存在的理由）。

A/B 的共同病：**97% / 83% 的输出挤在最高两档** —— 一个"分数"如果几乎没有方差，**根本无法用于排序**，
不管它准不准。C 是唯一能随措辞调整出方差的形态（两个方向都能到），说明这条问法"有控制力"，
但也说明**必须标定后才能定阈值**。
→ **Jev 的正确用法是"回答可证的是非（noul）/ 从给定选项里选（choice）"，不是"给绝对刻度（score）"**；
档位合成留在我们代码里（官方设计要点也正是"权重与逻辑留在调用方"）。

C 也暴露了下一处要改的地方：`COP31 缔约国会` 被判成"常规级"（假阴性）——说明 `is_routine` 的措辞
（"普通条目"）太宽，应改成**可数判据**（如"是否含可验证的事实信息：数字/政策/技术/协议/资金"），
而不是靠"普通/重要"这种主观形容词。

- `noul` 的回答**不带 `confidence`**（返回只有 `{noul, type}`）→ §4.3 的"置信度路由"只对

### 8.1 先回答"上次为什么跑不起来"

| 层 | 事实 | 结论 |
|---|---|---|
| 主流程 | `green-policy.service` 每轮 `77/77 源 ok`、`Succeeded` | **主流程没坏**（唯一 failed 单元是无头无关的 `kdump.service`） |

（附带踩坑：手工 scp 的 `.sh` 若带 CRLF，`KEY=$(cat file)` 会取到带 `\r` 的值 → 请求头变空 → TypeSafe 回 **403「Must supply an API key」**，看着像密钥错，其实是换行符。**远端脚本必须先 `-replace "\r\n","\n"`**。）

### 8.2 方案：服务器直连，不依赖 PC

实测服务器 → `https://api.typesafe.ai/v1/systemone` 直连可达（GET 405 路由存在 0.21s；带 key POST 200，**p50 0.29s**），因此选 **B 案（native 直连）**：

| 方案 | 判定 |
|---|---|
| **A. 服务器直连 TypeSafe（采用 ✅）** | 无需任何中间件、无 PC 依赖、延迟最低 |
| B. SSH 反向隧道回 PC 网关 | ❌ 否决：PC 必须常开，链路更脆 |
| C. 服务器再起一个 TokenHub | ❌ 否决：更重，且仍要同一个上游 key |
